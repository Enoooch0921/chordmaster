# 5 秒同步流量實測（2026-11-06）

## 結論

已實作公開分享、登入後共享工作區，以及自己的／團隊曲庫的條件式同步。自己的／團隊曲庫還支援逐筆差異下載、比較基準的無損傳輸及只寫入變動歌單項目。保留原有同步頻率。目前程式及 migration 在本機，尚未部署到正式站；NAS 驗證使用交易回滾，沒有持續修改正式資料庫。

## NAS HTTPS 實測

抽樣最近建立、仍有效的 8 個公開分享連結：5 份歌單、3 個活動。請求明確接受 gzip；伺服器確實使用 gzip。以下大小為壓縮後 HTTP 回應 body，不含 headers、TLS 或其他同步請求。未保存分享 token、帳號識別資料或歌譜內容。

| 範圍 | 每次回應 | 每人每小時 | 10 人連續 3 小時 |
| --- | ---: | ---: | ---: |
| 單份歌單（3～9 首） | 6,771～13,584 bytes | 4.88～9.78 MB | 0.146～0.293 GB |
| 整個活動（6～9 份歌單） | 76,914～102,917 bytes | 55.38～74.10 MB | 1.661～2.223 GB |

換算採十進位 KB/MB/GB，每小時約 720 次檢查。現有程式在請求結束後才等 5 秒，因此實際次數會隨回應時間減少；頁面隱藏、離線或錯誤退避也會減少次數。這是持續前景使用的情境估算，不是過去兩週實際流量，也不是 Supabase Cloud 帳單預測。

對其中一個活動相隔 5 秒再讀：兩次內容 SHA-256 完全相同，卻各下載 102,917 bytes。可確認目前沒有因內容未變而省下下載。

## 登入後的共享資料

以最近兩週有登入／token 續期的 20 個帳號，使用各自的 authenticated 使用者範圍，以唯讀交易執行現有 `get_joined_setlists`、`get_joined_projects`：19 個帳號有加入共享內容。

- 兩個 RPC 合計未壓縮 JSON：31,154～1,008,034 bytes，中位數 103,853 bytes。
- 這些是回傳 JSON 序列化大小，**不是量到的 HTTP 壓縮後大小**，不可直接與上表比較。
- 登入者目前會讀取所有已加入的歌單／活動，並非只讀正在看的那一首。
- 本次沒有加總個人 Capo 讀取、自己的曲庫／歌單更新、Realtime、登入或初次載入流量。

## 優化前的程式對照

- `src/hooks/useSharedResource.ts`：每次先取得完整回應，再在瀏覽器比較 JSON；目前省的是重新繪製，下載仍已發生。
- `src/hooks/useJoinedWorkspaceRefresh.ts`：有共享內容時，每次完成後等 5 秒再讀整個共享工作區。
- `src/lib/repository.ts` 的 `loadJoinedWorkspace`：並行讀取已加入歌單及活動，再讀個人 Capo。
- `src/hooks/useLibraryWorkspaceRefresh.ts`：另一條更新路徑；個人工作區設定 5 秒、團隊設定 15 秒，並每 5 分鐘或版本改變時重新抓曲庫。應另行評估，不可把共享路徑的節省率當成全站節省率。
- 已有離線／背景暫停、恢復前景立即檢查、避免重疊請求，以及本機修改期間的保護，應保留。

## 第一階段實作

1. 保持既有輪詢頻率及 Realtime 更新通知。首次載入取得完整資料和伺服器內容版本。
2. 後續請求附帶上次成功接受的版本；伺服器每次重新驗證登入者權限或分享連結的撤銷／到期狀態。
3. 從同一份授權後資料快照計算版本。版本相同只回傳小型確認；不同則直接回傳最新資料與版本，不增加一次「檢查後再下載」的往返。
4. 登入 RPC 必須在資料庫端省略未變的完整結果；公開分享則在服務端省略。僅在瀏覽器比對資料無法減少流量。
5. 版本涵蓋歌譜內容、Key、歌曲順序、新增刪除、個人 Capo、活動／歌單欄位、來源封存及權限等實際回傳資料，不能只看歌單本身的 `updated_at`。
6. 若回應因本機編輯或切換帳號／範圍而未被接受，不可提前推進版本。斷線後重試、權限撤銷及空結果仍需正常生效。

用 64 字元內容摘要組成的 `{version, unchanged: true}`，Edge handler 的實際測試回應為 95 bytes（尚未部署）。與 102,917-byte 活動回應相比，未變動回應的 body 可減少超過 99%；實際總節省率還要計入 headers、首次載入及修改後下載。這一步主要省網路傳輸，不代表資料庫計算量同等下降。

驗收應包含兩個使用者的歌譜／Key 修改、排序、新增刪除、個人 Capo、撤銷分享與成員資格、斷線恢復、背景回前景，以及未儲存編輯與舊回應競爭。再以同一批資料量壓縮後流量及同步延遲。

第一階段不包含按歌譜傳送差異；本文件後面的第二階段已補上自己的／團隊曲庫逐筆更新。公開分享與加入共享工作區目前仍是在內容改變時回傳該範圍完整內容。

另外，版本確認仍會保留請求次數。公開分享程式另有每 IP 每分鐘 120 次限制；同一網路 10 台裝置每 5 秒輪詢已接近此值，特會多人共用網路時應另行驗證，不能只驗收單人流量。

官方流量定義：[Manage Egress usage](https://supabase.com/docs/guides/platform/manage-your-usage/egress)。NAS 實測不能直接視為 Cloud 計費用量。

## 實作與驗證紀錄

- 新增 `get_joined_workspace_snapshot(p_known_version)`，以 `SECURITY INVOKER` 執行，只授權 authenticated；沒有增加資料表存取權限。使用原有每人範圍的 RPC，並把可見項目的個人 Capo 納入同一份版本。
- SHA-256 摘要來自當次完整授權內容，登入版也包含使用者 ID；版本不是存取憑證，每次仍重新讀取授權後資料。
- 公開 Edge Function 僅在新客戶端傳入 `conditional: true` 時使用新格式。舊前端仍取得原有回應；新前端也可讀舊後端的完整回應。
- 新 RPC 尚未部署時，前端只針對「函式不存在」退回原本讀法；網路或權限錯誤不當成空歌單或未變更。
- 前端版本與目前頁面／帳號綁定；本機狀態已變更或回應因編輯被忽略時，不採納該版本。
- NAS 真實資料回滾測試：首次 JSON **1,077,799 bytes**，第二次未變回應 **98 bytes**，確認不含 payload，且交易後新函式不存在。這兩者都是未壓縮 JSON 大小；不要與前面的 gzip HTTPS 實測混為一談。
- 新資料庫測試 70 個 SQL statements 通過：來源曲譜、私有副本、Key、個人 Capo、排序、新增刪除、成員撤權、角色降級、跨帳號隔離與匿名拒絕。原有團隊管理／成員範圍／權限／邀請四組回歸測試也通過。
- 公開 Edge handler 測試實際執行路由：舊版相容、未變回應、修改後新內容、分享撤銷／過期／不存在、限流拒絕；前端測試涵蓋斷線恢復、前景恢復及競爭回應。
- 完整 Vitest 回歸：210 個測試檔、2,371 項測試通過；TypeScript 檢查、網頁 production build、iPad build 均通過。建置仍有既有大型 chunk 提示。
- 既有 `security_definer_acl.sql` 最後的「未來函式預設權限」檢查仍失敗；已排除本次 migration 重跑，確認基線同樣失敗，詳見 `docs/team-administrators.md`。本次函式是 invoker 且有明確撤權，相關斷言通過。

## 上線順序

1. 僅在 NAS 依序套用 `20261106064633_conditional_joined_workspace.sql`、`20261106071039_library_workspace_delta.sql`，並確認 PostgREST 已更新函式快取。不可套用至歷史 Supabase Cloud 專案。
2. 在 NAS 部署 `resolve-share-link/index.ts` 及新增的 `_shared/conditionalResponse.ts`，保留現有 rateLimit helper。
3. 部署含這次修改的前端；目前工作區另有其他進行中的功能修改，上線時需明確選取要發布的內容。
4. 驗證新前端第一次完整取得資料，之後每 5 秒收到未變確認；另一裝置修改後，同一輪詢請求收到新內容。再驗證撤權與離線恢復。

可先單獨部署後端，舊前端行為不變；前端或 Edge 回滾時保留相容讀法。每 IP 限流策略不在這次修改範圍。

## 第二階段：四項優化

1. **自己的／團隊工作區條件式同步**：新增 `get_library_workspace_delta`。歌曲、歌單、活動、歌單項目、本人編輯指派與個人 Capo 納入同一個授權快照。未變更只回傳確認。個人原有 5 秒、團隊原有 15 秒間隔，以及 Realtime、回前景與重連觸發均保留。
2. **減少來源比較基準傳輸**：資料庫內完整 `source_baseline` 保留。傳輸時以當次來源歌譜為參考，只傳回還原舊基準所需的欄位差異；前端重建完整歷史來源與私有副本基準，因此既有來源狀態、差異比較與草稿邏輯不變。來源不可見時使用原有完整基準格式。陣列整段替換，明確區分 null、刪除與巢狀物件差異。
3. **只寫變動歌單項目**：比較既有快照的來源 ID、順序、Key、段落順序和私有歌譜。修改一首不再 upsert 其他未變項目；排序只寫移動的位置；刪除只刪原快照中明確移除的 ID，保留別人新增的項目與其他人的 Capo。團隊刪除使用額外角色檢查 RPC，舊後端保留原有角色預檢退路。這不是同一首歌譜的欄位衝突合併機制。
4. **曲庫逐筆下載**：每筆實際 JSON 的 SHA-256 版本和完整可見 ID 清單用來辨識新增、修改、刪除、撤權。只傳有變的歌曲／歌單等資料列，匯入保留原時間戳仍能抓到改變。首次條件式同步取得完整快照；後續不再每 5 分鐘強制下載全部曲庫。

### 同步與權限保護

- 新 RPC 使用 `SECURITY INVOKER`、空 search_path、明確 EXECUTE 權限，每次依使用者 RLS 重新讀取。版本清單不是存取憑證。
- 以一個資料庫 statement 的一致快照產生來源、基準、版本與差異，避免前後兩次查詢讀到互不相容的資料。
- repository 的傳輸快取與 React 已接受的儲存基準分離。編輯中忽略的回應會保留完整快照，下一次即使收到「未變」也能補上；不會把它提前當成本機已儲存基準。
- 請求依 repository 序列化、可取消；帳號／曲庫快取隔離，最多保留三個曲庫。缺資料、跨範圍回應或網路錯誤不推進快取，只有明確「RPC 不存在」才退回舊讀法。
- 原始啟動／切換曲庫的 `getLibraryWorkspace` 讀法仍保留；本次主要優化後續持續同步。首次進入仍可能先讀原有完整資料，再建立差異同步快取，不應把後續節省率套用到首次載入。

### NAS 回滾實測

以最大團隊曲庫的實際授權資料測試：640 首歌曲、86 個歌單項目。新函式只在交易內建立，測完回滾，沒有改寫正式歌譜或持續部署 schema。以下均是未壓縮 JSON body 大小，不含 HTTP headers/TLS。

| 項目 | 測量結果 |
| --- | ---: |
| 首次差異協定完整快照 | 6,414,977 bytes |
| 未變更回應 | 102 bytes |
| 下次請求的版本清單 | 88,455 bytes |
| 原完整比較基準合計 | 1,874,134 bytes |
| 無損差異基準合計 | 101,468 bytes（減少 94.59%） |
| 首次快照資料庫執行時間 | 1,344.656 ms |
| 未變更確認資料庫執行時間 | 604.127 ms |

86 筆基準已在實際 TypeScript 還原程式逐筆深度比對，完整 JSON 完全一致。另以客戶端只缺一首的版本清單讀取，實際回傳恰好一首歌曲、零筆歌單項目，沒有重傳其他 639 首。首次查詢避免反覆拼接越來越大的 JSON，改採一次聚合；兩次連續查詢的 EXPLAIN ANALYZE 執行時間由約 15.02 秒降至約 2.12 秒。上述分次時間是另一輪量測，屬單次樣本，並非多人併發或網路端到端延遲保證。

102 bytes 僅代表未變時的**下載回應**；仍有約 88 KB 版本清單上傳、HTTP 固定成本及伺服器讀取／雜湊運算。不可宣稱整體網路或資料庫負載也減少同樣比例。640 首歌曲的版本每次重新依授權資料計算，未來規模增加仍須觀察 CPU／查詢延遲。
