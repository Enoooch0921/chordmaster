這份建議以目前工作區原始碼、手機／平板／電腦尺寸的實際渲染，以及合成本機資料為依據；不是正式站或實體 iPad 的驗收。應用程式與 NAS 歌曲未修改。評估重點是敬拜團準備歌單、排練調整及現場閱讀。

## 整體判斷

優先改善大型曲庫搜尋、跨歌曲切換、手機演出閱讀，以及跨搜尋選曲的可見性。現有綠色視覺、平面列表、清楚的 Key／BPM 控制適合這項產品，應延續。已有離線快取、版本比較、排序、多選、拼音／注音／歌詞搜尋、演出滑動及鍵盤翻頁，不應重做或誤列為缺少。

## 五項優先問題

### 1. [P1] 搜尋與跨歌曲切換的更新範圍過大

曲庫排序／搜尋在 App 主體每次更新時執行，全部結果直接建立列。搜尋輸入直接更新 App state。歌單選中歌曲改變時，整份預覽歌曲陣列會重新建立每首的 song 物件，降低已加上的 memo 效果；一般連續譜面仍在演出覆蓋層背後存在。這些是應用 profiler 進一步拆分的成本來源，不能只依程式碼推定每一毫秒的歸因。

建議：將搜尋輸入與結果更新隔離於譜面；依真正變動的歌曲更新索引、排序及列；大清單僅渲染可見範圍；讓未改變歌曲保留物件身分；演出只更新當前歌曲，預先準備下一首。保留已有效的同曲直接翻頁路徑。不要靠加長動畫或固定延遲掩蓋卡頓。

來源：`src/App.tsx:3068`、`:13002`、`:13113`、`:10410`、`:10492`、`:15981`；`src/components/SetlistPreviewSong.tsx`。建議工作：impeccable optimize。

### 2. [P1] 手機演出整張 A4 太小，現場操作缺少歌曲層級導航

390×844 畫面把完整 A4 縮入窄螢幕，簡單和弦也顯得細小；上下黑邊不能改善受寬度限制的文字大小。平板與桌機的完整頁閱讀較合適。

建議：保留整頁／雙頁模式，新增手機「大字分段」閱讀，只改呈現，維持原始小節、反覆、段落與譜面內容；臨時看曲目時以緊湊抽屜顯示歌曲並可直接跳歌。最後一頁提示「下一首：歌名 · Key · BPM」，首尾頁提供清楚邊界。手機提供更直接的演出入口，目前入口在更多選單內。

此外，手機首次翻頁提示與「個人筆記」按鈕重疊，應共同安排底部位置。一般演出瀏覽可補螢幕常亮及返回前景後重新取得；目前找到的 Wake Lock 位於節拍器播放流程。既有離線快取上可加簡短的「本歌單已備妥／尚有內容未備妥」資訊，不必每次強制經過檢查視窗。

來源：`src/utils/performanceLayout.ts`、`src/App.tsx:7670`、`:16074`、`:16161`、`src/hooks/useMetronome.ts:142`、`docs/offline-workspace-startup.md`。

畫面：[手機演出](../output/playwright/ux-assessment-b-20261106/performance-phone.png)、[平板演出](../output/playwright/ux-assessment-b-20261106/performance-tablet.png)。建議工作：impeccable adapt、shape、harden。

### 3. [P1] 曲庫批次操作對同一組「已選歌曲」採用不同範圍

跨搜尋選取後，分享只取當前結果的已選歌曲，封存／刪除取完整選取集合，取消全選也僅清除目前結果。既有「其他搜尋結果中還有 N 首」提示有幫助，但操作規則仍需記憶。

建議：提供可檢視的「已選 N 首」清單與「清除全部」，讓各批次動作採用一致範圍；必須保留不同範圍時，明寫「分享目前結果 N 首」「封存全部已選 N 首」。

來源：`src/App.tsx:13044`、`:7346`、`:11274`、`:7358`。建議工作：impeccable clarify、shape。

### 4. [P2] 編歌單缺少跨搜尋待加入順序的集中檢查

現有加入歌曲支援多選、重複次數及按點選順序加入；但畫面只有總數，無法集中核對先前搜尋的歌名、版本與重複項目。返回會清空待加入內容。根層搜尋也會隱藏專案列；空專案無法直接按名稱找到。

建議：加入可展開的「已選歌曲」清單，按實際順序呈現，允許移除及排序；手機以底部清單呈現，平板／桌機可並排。搜尋同時回傳專案與歌單，歌單顯示父專案。未來可加入聚會日期、「複製上次聚會」及最近使用入口，這些屬產品擴充。

保留現有大尺寸 Key／BPM 列作編排用途。排練／演出另用緊湊導航，不縮小所有既有觸控目標。將設定影響範圍以情境文字呈現，例如「本次歌單」「只影響我的顯示」，不在每列反覆增加標籤。

來源：`src/App.tsx:6024`、`:6051`、`:12440`、`:12478`、`:3120`、`:12032`。建議工作：impeccable shape、clarify。

### 5. [P2] 曲庫搜尋結果未說明命中原因

歌詞、拼音、注音等能力已存在。結果只顯示曲名、作者／版本與音樂資訊，使用者輸入一句歌詞後，仍可能需要逐首打開。

建議：搜尋時增加命中歌詞片段或欄位提示；同名歌曲保留版本／作者識別；另提供最近使用、收藏及可收合的 Key／BPM／拍號篩選。不要把所有篩選常駐在手機頂部。

來源：`src/lib/songSearch.ts:174`、`:237`、`src/App.tsx:13132`。建議工作：impeccable clarify、shape。

## 各裝置的工作分配

| 裝置 | 建議 |
|---|---|
| 手機 | 仍保留完整編輯能力；常用動作靠近拇指區，已選清單可展開，演出有大字閱讀；避免多個浮動提示爭用同一底部區域。 |
| 平板 | 橫向以清單＋譜面並看為主，直向讓譜面優先；開關編輯器、旋轉及收起清單維持目前歌曲與閱讀位置。 |
| 電腦 | 支援密集資料整理、連續多選、鍵盤搜尋與排序；選曲結果和待加入清單並排。無須把手機的大型控制比例全部搬到桌機。 |

UI 延續綠色、平面列表與清楚選取狀態；主要任務按鈕附短標籤，次要管理留在選單。觸控主操作建議至少 44×44 CSS px；這是 W3C 增強目標尺寸準則，不應錯稱所有情況的 AA 最低門檻。[W3C](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)

常亮可被系統釋放或拒絕，須顯示實際狀態、返回前景重新取得，不能保證所有裝置永不熄屏。[MDN](https://developer.mozilla.org/en-US/docs/Web/API/Screen_Wake_Lock_API)

以下為啟發式判斷，非使用者研究或全面無障礙認證。獨立 A 初評 29/40；整合手機實際畫面與本機延遲後，效率、美感／閱讀各下調一分。

熟練使用者的主要負擔是搜尋後核對、排列與跨歌等待；新使用者容易混淆批次影響範圍；分心的手機使用者難以從選取總數重建先前選曲脈絡。一般曲庫瀏覽認知負荷低，跨搜尋多選與批次管理為中等。找到歌曲、進入簡潔演出畫面是高點；提交待加入內容及曲末跨歌曲之前最需要確定感。

## 建議執行順序

1. 大曲庫搜尋與跨歌曲切換，先用正式建置／實體裝置確認，再針對 profiler 熱點處理。
2. 手機演出提示重疊、入口、下一首預告與跳歌。
3. 跨搜尋已選清單及一致的批次範圍。
4. 手機大字分段閱讀、曲庫命中摘要與篩選。
5. 日期、常用模板／最近使用等擴充。

後續決策：優先選「速度」「歌單編排」「手機演出」；手機閱讀可選「保留整頁並新增大字模式」或「優先改善目前縮放操作」。
